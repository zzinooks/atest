# REA — Reverse Engineering Anything

목표: 대상(Target)을 **관찰 → 분해 → 가설 → 검증 → 재구성** 순으로 역설계해,
"이것을 처음부터 다시 만들 수 있는 사람"이 읽을 수 있는 **블루프린트**를 남긴다.

핵심 원칙
1. **관찰과 추론을 분리한다.** 모든 주장에 근거 등급을 붙인다.
   - `[확인]` 직접 관찰·실행·원문으로 확인함
   - `[추론]` 관찰된 증거로부터 논리적으로 도출함 (근거를 함께 적는다)
   - `[가정]` 증거 없이 일반적 관행에 기대어 둔 가설 (검증 방법을 함께 적는다)
2. **바깥에서 안으로.** 경계(입력/출력/인터페이스)를 먼저 고정하고 내부로 들어간다.
3. **"왜"까지 간다.** 구조(What)와 동작(How)에서 멈추지 않고 설계 의도·제약(Why)을 복원한다.
4. **재현으로 증명한다.** 가능하면 최소 재현(프로토타입·시뮬레이션·샘플)을 만들어 원본과 비교한다.
5. **합법·윤리 범위 안에서.** 아래 "범위와 한계"를 지킨다.

---

## 0단계 — 범위 확정 (Scoping)

시작 전에 다음을 정한다. 명확하면 묻지 말고 기본값으로 진행하며, 정한 내용을 한 줄로 밝힌다.

| 항목 | 질문 | 기본값 |
|---|---|---|
| 대상 | 무엇을 역설계하나? 어떤 형태로 주어졌나(파일·URL·설명·로그·화면)? | 주어진 자료 |
| 목적 | 이해 / 재구현 / 개선 / 호환·연동 / 장애 분석 / 벤치마킹 중 무엇? | 이해 + 재구현 가능 수준 |
| 깊이 | L1 개요 · L2 구조 · L3 메커니즘 · L4 재현 | L3 |
| 산출물 | 블루프린트 문서 / 다이어그램 / 재현 코드 / 체크리스트 | 블루프린트 문서 |

대상 유형을 분류한다 → `references/target-playbooks.md`에서 해당 플레이북을 읽는다.
(소프트웨어·코드 / 바이너리·프로토콜 / 데이터·DB·로그 / 제품·UI / 문서·콘텐츠 / 업무 프로세스·조직 / 비즈니스 모델 / 물리 시스템·설비 제어)

## 1단계 — 관찰 (Observe): 블랙박스로 본다

내부를 열기 전에 겉에서 보이는 모든 것을 수집한다.
- **경계**: 입력, 출력, 외부 인터페이스, 의존 대상, 사용자/액터
- **행동**: 정상 시나리오, 예외 시나리오, 경계값, 타이밍/순서
- **흔적(Artifacts)**: 파일 구조, 이름 규칙, 버전/날짜, 로그, 설정, 에러 메시지, 메타데이터
- **불변식 후보**: 항상 성립하는 것처럼 보이는 규칙

산출: 관찰 목록 (모두 `[확인]`)

## 2단계 — 분해 (Decompose): 화이트박스로 연다

- 구성요소를 식별하고 **책임 1줄**씩 부여한다.
- 구성요소 간 **관계**(호출, 데이터 흐름, 제어 흐름, 소유/포함)를 그린다.
- **데이터 모델**: 핵심 엔티티, 상태, 식별자, 생명주기
- **상태 기계**: 주요 엔티티의 상태와 전이 조건 (대부분 시스템의 핵심은 여기에 있다)
- **계층**: 표현/로직/데이터/인프라 등 어느 층에 무엇이 있는지

도구가 있으면 실제로 쓴다: 코드 검색(Grep/Glob), 실행·트레이싱, `strings`/`file`/`xxd`/`objdump`,
DB 스키마 조회, 로그 집계 스크립트, 브라우저(Playwright)로 화면·네트워크 관찰 등.

## 3단계 — 가설 (Hypothesize): 메커니즘과 의도를 복원

각 구성요소/흐름에 대해:
- **How**: 어떤 알고리즘·규칙·순서로 동작하는가
- **Why**: 왜 이렇게 설계했는가 — 성능, 비용, 안정성, 규제, 레거시 호환, 조직 구조(콘웨이 법칙), 일정 압박
- **대안**: 다른 방법은 무엇이었고 왜 선택되지 않았을까
- **트레이드오프**: 이 설계가 포기한 것

가설마다 근거 등급과 **반증 조건**("이 관찰이 나오면 가설이 틀린 것")을 적는다.

## 4단계 — 검증 (Verify)

- 가설을 확인할 **가장 싼 실험**을 고르고 실행한다 (입력 변형, 로그 대조, 최소 재현, 원문 확인).
- 실행 불가하면 "검증 방법"만 구체적으로 남긴다.
- 결과에 따라 `[가정]→[추론]→[확인]`으로 등급을 갱신하고, 틀린 가설은 지우지 말고 "기각"으로 표시한다.

## 5단계 — 재구성 (Rebuild): 블루프린트 작성

`references/blueprint-template.md` 형식으로 최종 산출물을 작성한다. 필수 포함:
1. 한 문단 요약 (이것은 무엇이며, 핵심 메커니즘은 무엇인가)
2. 아키텍처/구성도 (텍스트 다이어그램 또는 Mermaid)
3. 데이터 모델 · 상태 전이
4. 핵심 흐름 시퀀스 (정상 + 대표 예외)
5. 설계 의도와 트레이드오프
6. 재현 가이드 — 처음부터 만든다면 순서와 최소 구성(MVP)
7. 미확인 사항 · 리스크 · 다음 검증 액션
8. 근거 등급 요약 (확인/추론/가정 비율)

깊이 L4이면 최소 재현물(코드·시뮬레이터·샘플 데이터)을 만들고 원본과 차이를 표로 비교한다.

## 출력 규칙

- 사용자의 언어로 쓴다 (기본 한국어). 용어는 원문 표기를 병기한다.
- 결론 먼저, 근거는 뒤에. 표·다이어그램을 적극 활용한다.
- 추측을 사실처럼 쓰지 않는다. 근거 등급이 없는 주장은 남기지 않는다.
- 산출물이 길면 파일(`rea-<대상명>.md`)로 저장하고 대화에는 요약 + 경로를 준다.

## 범위와 한계 (반드시 지킨다)

- 허용: 본인/소속 조직 소유 시스템, 정당한 권한이 있는 대상, 공개 자료, 상호운용성·보안 연구·교육·장애 분석·CTF.
- 거부: 라이선스·DRM·인증·결제 우회, 타인 시스템 무단 침투, 악성코드 제작, 개인정보 탈취,
  특정 상용 제품의 브랜드·자산·코드를 그대로 복제하는 것. 이 경우 이유를 짧게 밝히고
  합법적 대안(공개 API, 공식 문서, 클린룸 설계 원칙)을 제시한다.
- 재현 산출물은 **클린룸 원칙**을 따른다: 원본 코드·자산을 복사하지 않고, 복원한 명세로부터 새로 구현한다.
